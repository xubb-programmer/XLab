# 通信代理：扩展开发与迁移

## 1. 构建和运行

依赖 Qt 5 的 Core、Network、SerialPort、SerialBus 模块，以及 C++17 编译器、qmake、libmosquitto、spdlog、fmt、nlohmann/json。MQTT 集成测试还需要本地 mosquitto、mosquitto_pub/sub 和 Python 3。

Linux/WSL 从项目根目录执行：

```bash
mkdir -p EdgeAgent/build-proxy
cd EdgeAgent/build-proxy
qmake ../EdgeAgent.pro
make -j4
./edgeagent --config ../config.json
```

Windows Qt Creator 打开 `EdgeAgent/EdgeAgent.pro`，选择安装所需依赖的 Qt Kit。原生 Windows 和设备驱动仍需单独验证。CAN 默认后端为 Linux SocketCAN。

图形测试工具独立构建：打开 `EdgeAgentTester/EdgeAgentTester.pro`。

## 2. 配置迁移

原有 v1 UDP/TCP/串口/CAN 配置继续使用，通道内的 device_id 和 qos 会转换为内部绑定。

项目仓库仅保留一份 config.json，原有分场景配置文件已合并。所有类型集中在 channels 中，使用 enabled 切换；默认 UDP 单播和 TCP 服务端开启，TCP 客户端、串口、CAN、UDP 组播关闭。修改参数后按需开启，Windows 串口名需改为实际 COM 端口。

从 build-proxy 运行时使用上述 --config 路径。如果部署为独立程序，可将这份配置随程序放置为同目录 config.json，随后无需指定参数。配置修改需重启。

v2 使用 channels + devices，每通道最多一个设备绑定。设备绑定保存 device_id、channel_id、qos 和可选 message_format；已有 protocol=transparent 声明可以保留或删除。设备控制和采集策略由业务服务管理。

数据及回执输出默认采用统一 JSON。现有消费者若需要保持原格式，v1 在通道内、v2 在设备内显式添加 `"message_format":"legacy"`。旧下行别名和 TCP/串口原始正文继续支持；不要在一个发送信封里混用新旧字段。

TCP/串口必须从 delimiter、fixed_length、length_prefix、idle_timeout 中选择接收分帧方式。若设备依靠静默界定报文，可使用 idle_timeout，并结合设备时序选择 idle_ms；它不是设备报文校验器。

## 3. 接入新的设备报文

只要设备通过现有四类接口通信，业务服务就可以生成字节并经 commands 发送，再订阅 data 解释响应，无需向代理添加设备驱动。

业务服务自行维护轮询、响应匹配、CRC/校验、超时和重试。写操作发生超时或断线时，应结合设备状态决定后续处理。

## 4. 新增物理通信方式

1. 继承 Channel，实现 start、stop、send。
2. 接收时生成 FrameEvent，保留来源元数据。
3. 发出统一状态和 fault 信号。
4. 扩展配置模型、解析、EdgeAgent 通道装配及 TransportCodec 参数验证。
5. 复用统一信封和 meta.endpoint/connection/frame 语义，增加往返编解码及适用性测试。

详细字段、Topic、消息 ID 和向后兼容约定见文档 03。新增可选属性应保持既有字段语义；破坏性更改需使用新的 Topic 版本。

Channel 不应直接调用 MQTT。新的传输必须明确本地发送成功的含义、接收边界、资源限制和恢复行为。
