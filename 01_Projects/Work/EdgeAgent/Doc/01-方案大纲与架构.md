# 方案大纲与架构

## 职责划分

| 组件 | 职责 |
| --- | --- |
| EdgeAgent | 打开现场接口，管理连接，划分接收帧，上报传输元数据，将下行字节提交给接口并发布发送回执 |
| MQTT Broker | 在代理与业务服务之间路由消息，处理订阅、QoS、保留消息和遗嘱 |
| 业务服务 | 生成和解析设备报文，管理地址、CRC、轮询、响应匹配、业务超时和重试 |

设备返回的字节走独立的上行链路。每条上行数据有自己的消息 ID，设备请求与应答的关联由业务服务完成。

## 通道与 Topic 绑定

`ChannelConfig` 描述一个物理资源，例如 UDP socket、TCP 监听器或客户端、串口或 CAN 接口。`DeviceConfig` 使用 `channel_id` 关联该资源，并提供 `device_id`、上行 QoS 和输出格式。一个通道最多绑定一个设备 ID，由此生成一组设备 Topic。同一串口或总线上的设备地址留在设备报文中。v2 允许启用未绑定的通道，其接收数据只记录日志。

`enabled` 控制整个通道。启动时先校验配置与引用，再剔除禁用通道和对应设备绑定。禁用通道无需打开物理资源，也没有对应的 MQTT 订阅。详细约束见 [03 配置与接口契约](03-配置与接口契约.md)。

## 数据流

```text
现场接口 → Channel → FrameEvent → EdgeAgent → TransportCodec → data Topic
commands Topic → EdgeAgent → TransportCodec → TransportCommand → Channel::send()
                                         处理结果 → command-results Topic
```

- `Channel` 提供 `start()`、`stop()` 和 `send()`，通过 Qt 信号交付接收帧、状态和故障。
- `FrameEvent` 保存接收字节、时间和来源。UDP 与 CAN 使用数据报或总线帧的边界，TCP 与串口使用各自的接收分帧配置。
- `TransportCommand` 保存待发送字节及目的地址、连接或 CAN 帧属性。TCP 与串口发送完整的调用方字节，帧头、长度和分隔符由调用方准备。
- `EdgeAgent` 负责 Topic 路由、调用通道和生成回执。`TransportCodec` 负责解析命令并编码 JSON 数据和回执。

## 通道能力

| 通道 | 接收边界 | 统一格式下行定位 |
| --- | --- | --- |
| UDP | 一个数据报 | 必填目标 IP 和端口，须命中对端白名单 |
| TCP 客户端或服务端 | 按配置拆分字节流 | 用连接 ID、对端 IP 和端口或两者筛选，必须唯一匹配已建立的连接 |
| 串口 | 按配置拆分字节流 | 使用配置的串口 |
| 经典 CAN | 一个标准帧、扩展帧或远程请求帧 | 使用配置的 CAN 接口，并提供 CAN ID 及适用帧属性 |

`sent` 确认本地发送接口接受了数据。设备收妥、执行结果和业务确认通过设备协议判断。网关状态表示 Broker 连接，通道状态单独记录在日志中。
