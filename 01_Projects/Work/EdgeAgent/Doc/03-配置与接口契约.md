# 通信代理：配置与接口契约

## 1. Topic 是消息地址

MQTT 消息由 Topic 和正文组成：Topic 决定消息发布到哪个频道，正文保存 JSON 数据，两者分开传递。

| Topic | 方向及用途 |
|---|---|
| edge/v1/devices/{device_id}/data | 代理发布，业务程序订阅设备数据 |
| edge/v1/devices/{device_id}/commands | 业务程序发布，代理订阅下发消息 |
| edge/v1/devices/{device_id}/command-results | 代理发布发送回执 |
| edge/v1/gateways/{node_id}/status | retained online / 异常断线遗嘱 offline |

例如 `edge/v1/devices/motor_01/data`。device_id 来自配置，而不是消息正文；所有通信方式使用相同 Topic 规则。业务程序可订阅 `edge/v1/devices/+/data` 接收所有设备数据。当前 Topic 不可自定义。

## 2. 统一 JSON 信封

默认 message_format=json。四种通道的数据上行使用相同字段：

```json
{
  "id": "自动生成的UUID",
  "ts": 1794225600000,
  "transport": "udp",
  "data": "A1B2",
  "meta": {
    "endpoint": {"address": "192.168.1.20", "port": 9000}
  }
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| id | 非空字符串 | 当前消息的标识 |
| ts | 非负整数 | 代理接收时间，Unix 毫秒时间戳 |
| transport | 字符串 | udp、tcp、serial、can |
| data | 字符串 | 大写 HEX，每两个字符一个原始字节；允许空正文 |
| meta | 对象 | 同一套端点、连接、帧属性模型 |

上行五个字段均存在。下行必须有 data，其他字段按需填写：id 省略时自动生成；ts 仅作附加信息，不控制定时发送或有效期；transport 省略时从配置推导，填写时必须一致；meta 根据通道要求填写。

HEX 不接受空格、奇数长度或非十六进制字符。下行整个 MQTT 正文最多 1MiB，包含 HEX 和 JSON 开销。

## 3. 统一 meta 字段及语义

meta 始终为对象；不存在针对某个通道另起的 peer、can、serial 等分支。

| 字段 | 含义 | 约束 |
|---|---|---|
| endpoint | 通信端点对象 | 上行表示来源端点，下行表示目标端点 |
| endpoint.address | 端点地址字符串 | 网络填 IP；串口填端口名；CAN 填接口名 |
| endpoint.port | 网络端口整数 | UDP/TCP 使用，1..65535；本地接口禁止填写 |
| connection | 当前连接标识字符串 | 仅 TCP 使用，标识一条已建立连接 |
| frame | 帧属性对象 | 当前由 CAN 使用；帧标识与通信端点分开 |
| frame.id | 帧标识字符串 | CAN 的 0x 前缀十六进制 ID |
| frame.extended | 布尔值 | 默认 false，CAN 扩展帧设为 true |
| frame.remote | 布尔值 | 默认 false，CAN 远程请求帧设为 true |
| frame.length | 非负整数 | CAN 0..8；普通帧默认由 data 计算，远程帧必须填写请求长度 |

省略无意义字段，不填 null、空字符串、虚构端口或重复的默认值。普通 CAN 帧上行不输出可计算的 length，也不输出值为 false 的标志。端点地址不拼接端口，IPv6 也无需拆分字符串。

### 四种通道的 meta 实例

UDP：

```json
{"endpoint":{"address":"192.168.1.20","port":9000}}
```

TCP：

```json
{"endpoint":{"address":"192.168.1.20","port":9000},"connection":"server-12"}
```

串口：

```json
{"endpoint":{"address":"/dev/ttyUSB0"}}
```

CAN：

```json
{"endpoint":{"address":"can0"},"frame":{"id":"0x123"}}
```

### 下行规则

- UDP 必须提供 endpoint.address 和 endpoint.port，并符合 allowed_peers。
- TCP 可提供 connection、endpoint 或两者；两者同时提供必须匹配同一条连接。统一命令必须唯一匹配一个已连接目标，多个目标时不任意选取。endpoint 不会创建新 TCP 连接，使用连接上报的实际 IP。
- 串口/CAN 的 endpoint 可省略；填写后必须与配置的本地接口一致，不能动态切换接口。
- CAN 必须提供 frame.id；标准 ID 上限 0x7FF，扩展 ID 上限 0x1FFFFFFF。普通帧 length 若提供必须等于数据字节数；远程帧 data 必须为空且 length 必填。
- 不适用的 connection、frame、port，以及未知字段、错误类型和新旧字段混用均拒绝，避免静默忽略参数。

上行 meta 可直接用作定向回复的 meta，但连接断开后原 connection 不再有效。TCP/串口上行已经移除接收分帧的分隔符或长度头；回复仍需自行提供完整发送字节。

## 4. 下行及回执示例

串口或唯一 TCP 连接：

```json
{"id":"cmd-001","data":"A1B2"}
```

UDP：

```json
{"id":"cmd-002","data":"A1B2","meta":{"endpoint":{"address":"192.168.1.20","port":9000}}}
```

指定 TCP 连接：

```json
{"id":"cmd-003","data":"A1B2","meta":{"connection":"server-12"}}
```

CAN：

```json
{"id":"cmd-004","data":"A1B2","meta":{"frame":{"id":"0x123"}}}
```

发送成功回执：

```json
{"id":"cmd-001","status":"sent"}
```

失败回执：

```json
{"id":"cmd-001","status":"failed","error":{"code":"invalid_request","message":"发送命令字段缺失、类型错误或超出范围"}}
```

sent 只代表本地接口接受数据，不代表设备已收到或执行。错误码包括 invalid_json、invalid_request、payload_too_large、retained_command、unknown_device、stopped、send_failed。

## 5. 消息 ID 的产生和使用

上行由代理为每条消息生成 UUID。下行建议业务程序生成 id，代理原样用于回执；省略则生成 UUID，合法统一命令中的空 id 或非字符串 id 会被拒绝。

id 与设备 ID、TCP 连接标识、CAN 帧 ID 是四个不同概念。设备返回的数据产生新的消息 id，代理不自动将其关联为下行的业务应答；业务服务按设备报文自行关联。重复 id 不自动去重，也不保证只执行一次。

## 6. 配置版本及输出兼容

配置在启动时一次加载。config_version 默认 1。

- v1：每个 channels 项内保存 device_id、qos 和可选 message_format。
- v2：channels 保存物理参数，devices 保存 device_id、channel_id、qos 和可选 message_format。

message_format 只接受 json（默认）或 legacy，控制该设备的数据上行及发送回执。已有客户端需要显式设置 legacy 才保持旧输出；默认值改变不会自动迁移消费者。

新格式和旧格式下行都可被解析，不需要切换输出格式。旧下行保留 msg_id、operation=send、target_ip/target_port、connection_id、edge.can.v1 等字段；禁止与新 id/transport/meta/ts 混用。TCP/串口原始字节正文继续兼容；JSON 包含 data、operation、id、ts、transport、meta 任一控制字段时按发送信封处理，字段错误不会作为原始数据发送。

legacy 输出：UDP 为 edge.udp.v1 JSON，CAN 为 edge.can.v1 JSON，TCP/串口为原始字节；回执为原 edge.command-result.v1。旧结构不采用本文的统一 meta。

每通道最多一个设备绑定；设备 ID、通道 ID 分别唯一。v2 允许兼容的 protocol=transparent 声明，不加载设备驱动。标识长度 1..64，首字符为字母或数字，其余允许字母、数字、点、下划线、连字符。多个网关共享 Broker 时避免 device_id 冲突。

所有通道使用一份 config.json，通过各通道的 enabled 布尔字段启用/关闭，省略时为 true。关闭通道不打开接口、不连接、不监听、不启动重连，其对应设备也不订阅命令或发布数据。设备绑定无需另设开关。禁用模板仍校验字段、ID 和引用，避免启用后才发现配置错误。

## 7. 物理连接参数

统一配置见 [config.json](../EdgeAgent/config.json)。该文件同时包含 UDP 单播/组播、TCP 客户端/服务端、串口和 CAN，采用配置 v2。默认仅启用 UDP 单播 18080 和 TCP 服务端 18081；启用其他通道前修改对应地址、端口、串口名或 CAN 接口及分帧参数。

固定长度在相应 TCP/串口通道的 frame 内配置，例如 `{"kind":"fixed_length","length":16,"max_bytes":65536}`。length 包含设备报文头、正文和校验码，代理不解释这些设备字段。

Broker：host/port 默认 127.0.0.1/1883，protocol 只接受 mqtt311；client_id 默认 edgeagent-{node_id}；keepalive_s 默认 30，范围 10..120；clean_session 默认 true；可配置 username 和 password_env。订阅及回执 QoS 1，数据使用设备 qos（0/1）。

| 通道 | 主要配置 |
|---|---|
| UDP | bind_address、bind_port、allowed_peers；可选 max_datagram_bytes、multicast |
| TCP Client | role=client、remote_host、remote_port、frame、连接超时及重连间隔 |
| TCP Server | role=server、listen_address、listen_port、frame、max_clients |
| Serial | port_name、frame、baud_rate、data_bits、parity、stop_bits、flow_control、重连间隔 |
| CAN | interface、backend、filters、receive_own_frames、重连间隔 |

UDP allowed_peers 使用 IP:端口，端口 0 通配；同时限制来源和目标。串口默认 9600/8N1。CAN 默认 socketcan，bitrate 和 restart_on_bus_off 保留兼容字段，但接口比特率及 Bus-Off 恢复需外部配置。store_forward.enabled=true 会被拒绝。

TCP/串口 frame.kind 采用 delimiter（delimiter 字符串）、fixed_length（length）、length_prefix（length_bytes=1/2/4，byte_order=big_endian/little_endian）、idle_timeout（idle_ms）。max_bytes 默认 65536，范围 1..16777216。分帧只作用于接收方向，下行不自动补帧头或分隔符。

所有 commands 均拒绝 retained 消息。网关状态仍为 online/offline 文本，不属于设备数据信封；正常退出当前没有主动发布 offline。

## 8. 后续协议兼容约定

不同设备协议的任意二进制报文均可通过 data 透传，代理不解释业务字段。新增通信方式应优先复用 endpoint.address/port、connection、frame 的现有含义；不得把总线帧 ID 冒充设备地址，也不增加顶层 peer、can 等平行分支。

接收方应忽略未来新增的可选上行字段；发送方只发送目标版本支持的字段，当前下行严格校验，未知参数不会被静默执行。新增物理通道仍需实现对应 Channel 和参数适配，不是只改 transport 名称就能支持。破坏性结构或语义变化使用新的 Topic 版本，不复用现有字段表达不同含义。
