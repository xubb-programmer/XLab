# 配置与接口契约

## 配置文件

仓库的 [config.json](../EdgeAgent/config.json) 包含全部通道模板。配置在启动时加载，修改后重启生效。

| 字段 | 规则 |
| --- | --- |
| `config_version` | 支持 `1` 和 `2`，省略时为 `1`。示例配置使用 `2` |
| `node_id` | 必填，作为网关状态 Topic 的标识，也是默认 MQTT 客户端 ID 的一部分 |
| `channels` | 通道定义数组。每项须提供唯一的 `channel_id`、`type` 和对应通道参数 |
| `channels[].enabled` | 布尔值，默认 `true`。禁用项及其设备引用仍参与启动校验，通过后从运行配置中剔除 |
| `devices` | v2 必须提供非空数组。每项用 `channel_id` 引用通道，并声明唯一的 `device_id`。每个通道最多绑定一个设备 |
| `qos`、`message_format` | v1 与 `device_id` 一起放在通道内，v2 放在设备绑定内。QoS 为 `0`（默认）或 `1`。输出格式为 `json`（默认）或 `legacy` |

`node_id`、`channel_id`、`device_id` 长度为 1 至 64，首字符为 ASCII 字母或数字，后续还允许 `.`、`_`、`-`。多个网关共用 Broker 时，设备 ID 需要在共用的设备 Topic 命名空间内保持唯一。

v2 设备项支持 `device_id`、`channel_id`、`qos`、`message_format`，以及兼容字段 `protocol: "transparent"` 和 `store_forward`。`store_forward.enabled: true` 在通道或设备绑定中均会被拒绝。通道的旧字段 `mode` 可省略，保留时 UDP/CAN 使用 `json`，TCP/串口使用 `raw`。`mode` 与 MQTT 输出选项 `message_format` 分别校验。

### Broker 参数

| `broker` 字段 | 默认值与用法 |
| --- | --- |
| `host`、`port` | `127.0.0.1`、`1883`，端口范围 1 至 65535 |
| `protocol` | 仅接受 `mqtt311` |
| `client_id` | 默认 `edgeagent-{node_id}` |
| `keepalive_s`、`clean_session` | 分别为 `30` 秒和 `true`，保活范围 10 至 120 秒 |
| `username`、`password_env` | 用户名非空时传递认证信息。配置 `password_env` 后，指定的环境变量须存在且非空 |

### 通道参数

| `type` | 必填或角色相关字段 | 可选参数与默认值 |
| --- | --- | --- |
| `udp` | `bind_address`、`bind_port`、`allowed_peers` | `max_datagram_bytes` 默认 65507，范围 1 至 65507，双向生效。启用 `multicast.enabled` 时填写 `group`，`interface` 为空时使用系统选择的接口 |
| `tcp` 服务端 | `role: "server"`、`listen_address`、`listen_port`、`frame` | `max_clients` 默认 8，范围 1 至 1024 |
| `tcp` 客户端 | `role: "client"`、`remote_host`、`remote_port`、`frame` | `connect_timeout_ms` 默认 5000，至少 100。重连初始值至少 100 毫秒 |
| `serial` | `port_name`、`frame` | 默认 9600 波特、8 数据位、无校验、1 停止位、无流控。波特率范围 1200 至 921600 |
| `can` | `interface` | `backend` 默认 `socketcan`，`filters` 默认空，`receive_own_frames` 默认 `false` |

UDP 的 `allowed_peers` 是字符串数组，条目格式为 `IP:端口`，按最后一个冒号拆分。端口 `0` 匹配该 IP 的任意端口。收包按来源 IP 和端口检查，发包按目标 IP 和端口检查，空数组拒绝所有对端。组播组地址用于入组，组播上行的白名单仍检查实际发送方 IP 和端口。配置项 `broadcast` 为真时，当前代码设置的是组播 TTL 1。

TCP 客户端、串口和 CAN 使用 `reconnect_initial_ms` 和 `reconnect_max_ms`，默认 1000 和 60000 毫秒，最大值须不小于初始值。串口和 CAN 的两个参数均限于 100 至 3600000 毫秒。

串口 `data_bits` 允许 5 至 8。`parity` 允许 `none`、`even`、`odd`、`space`、`mark`。`stop_bits` 允许 1、1.5 或 2，其中 1.5 仅配合 5 数据位。`flow_control` 允许 `none`、`hardware`、`software`。驱动和平台还需支持所选参数。

CAN 过滤项需要 `can_id`，可提供 `can_id_mask` 和 `extended`（默认 `false`）。ID 和掩码为 `0x` 前缀的十六进制字符串，缺省掩码为标准帧的 `0x7FF` 或扩展帧的 `0x1FFFFFFF`。`bitrate`（默认 500000）和 `restart_on_bus_off`（默认 `true`）只解析和校验。使用 SocketCAN 时，在系统侧设置接口的波特率和 Bus-Off 恢复参数。

### TCP 和串口接收分帧

`frame.kind` 必填，`frame.max_bytes` 默认 65536，范围 1 至 16777216。TCP 和串口下行始终使用命令提供的完整字节。

| `kind` | 所需参数 |
| --- | --- |
| `delimiter` | `delimiter` 为非空 JSON 字符串，解码后按 UTF-8 用作分隔符。例如 `"\n"` 表示一个 LF 字节 |
| `fixed_length` | `length` 为每帧字节数，至少为 1 且不超过 `max_bytes` |
| `length_prefix` | `length_bytes` 为 1、2 或 4。`byte_order` 为 `big_endian`（默认）或 `little_endian`。前缀表示正文字节数 |
| `idle_timeout` | `idle_ms` 为静默间隔，至少 1 毫秒 |

## MQTT Topic

| Topic | 发布者 → 订阅者 | QoS 与保留 |
| --- | --- | --- |
| `edge/v1/devices/{device_id}/data` | EdgeAgent → 业务端 | 设备配置的 QoS，非保留 |
| `edge/v1/devices/{device_id}/commands` | 业务端 → EdgeAgent | 代理按 QoS 1 订阅，发布端应关闭 RETAIN |
| `edge/v1/devices/{device_id}/command-results` | EdgeAgent → 业务端 | QoS 1，非保留 |
| `edge/v1/gateways/{node_id}/status` | EdgeAgent 或 Broker → 业务端 | QoS 1，保留文本 `online` 或 `offline` |

Topic 由固定路径和配置中的 ID 生成。业务端可以用 `edge/v1/devices/+/data` 订阅所有设备上行。代理连上 Broker 后发布 `online`。`offline` 来自 Broker 的遗嘱，代理退出时请求断开 MQTT。Broker 收到 `DISCONNECT` 时丢弃遗嘱，先前保留的 `online` 仍可被订阅者读到。若连接关闭前该报文未送达，Broker 可发布 `offline`。[MQTT 3.1.1 §3.1.2.5 和 §3.14.4](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)

代理拒绝收到时仍带 RETAIN 标志的命令。MQTT 3.1.1 的 Broker 向已有订阅实时转发时会清除 RETAIN 标志，因此实时发布的保留命令仍可能执行。发布命令时应关闭 RETAIN。[MQTT 3.1.1 §3.3.1.3](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)

## 统一 JSON 信封

以下是 UDP 上行示例。设备 ID 在 Topic 中，正文包含固定的五个字段。

```json
{
  "id": "a4c2b3d5-95fb-4cfa-a303-1cd229a65c8a",
  "ts": 1794225600000,
  "transport": "udp",
  "data": "01020304",
  "meta": {
    "endpoint": {"address": "127.0.0.1", "port": 19090}
  }
}
```

| 字段 | 上行 | 统一下行 |
| --- | --- | --- |
| `id` | 代理生成的 UUID | 可选的非空字符串，原样用于回执。省略时生成 UUID |
| `ts` | 代理产出接收帧时的 Unix 毫秒时间 | 可选的非负 64 位有符号整数，校验后忽略 |
| `transport` | `udp`、`tcp`、`serial` 或 `can` | 可省略，填写时须与目标通道一致 |
| `data` | 大写 HEX 字符串 | 必填 HEX 字符串，大小写均可，长度须为偶数，允许空字符串。每两字符表示一个字节，只接受 `0–9`、`A–F`、`a–f` |
| `meta` | 端点及适用的连接或帧属性 | 对象。可省略的范围取决于通道 |

统一命令只接受表内顶层字段及下表中适用的 `meta` 字段。所有下行格式的整个 MQTT 正文限制为 1 MiB，JSON 和 HEX 文本均计入限制。UDP 另受 `max_datagram_bytes` 约束，经典 CAN 负载最多 8 字节。

### 元数据与目标匹配

| 字段 | 上行含义 | 下行约束 |
| --- | --- | --- |
| `meta.endpoint` | UDP/TCP 为实际对端 IP 和端口，串口/CAN 为配置中的接口名 | UDP 必填。TCP 可用于筛选已连接的对端。串口/CAN 可省略，填写时 `address` 须与配置完全一致 |
| `meta.endpoint.address` | 端点地址字符串 | 网络地址填 IP 字面量。串口填 `port_name`，CAN 填 `interface` |
| `meta.endpoint.port` | UDP/TCP 对端端口 | 网络端点须提供 1 至 65535 的整数，串口/CAN 端点禁填 |
| `meta.connection` | TCP 当前连接 ID | 仅 TCP 可用，非空字符串，从当前上行取得 |
| `meta.frame` | CAN 帧属性 | CAN 必填，其他通道禁填 |

TCP 统一命令可按连接 ID、对端 IP 和端口或两者筛选。两者同时填写时须匹配同一连接，两者均省略时须恰有一条已连接会话。匹配不到或存在多个候选时回执为 `send_failed`。TCP 客户端的下行目标同样来自连接表。服务端上行的端口是客户端源端口。重连后应使用新上行中的连接标识。

CAN 的 `frame.id` 为带 `0x` 前缀的十六进制字符串。`extended` 和 `remote` 为布尔值，默认 `false`。标准 ID 范围为 `0x000` 至 `0x7FF`，扩展 ID 最大为 `0x1FFFFFFF`。数据帧的 `length` 可省略，填写时须等于负载字节数。远程请求帧须提供 0 至 8 的整数 `length` 和空字符串 `data`。上行只在相应标志为真时输出 `extended` 或 `remote`，并只为远程请求帧输出 `length`。

### 下行示例

```json
{"id":"udp-01","data":"01020304","meta":{"endpoint":{"address":"127.0.0.1","port":19090}}}
```

```json
{"id":"tcp-01","data":"010203040A","meta":{"connection":"server-6abc2fe1-a981-47d9-8c93-42bf2ec70cbf"}}
```

TCP 示例需换成现场上行的连接 ID。末尾的 `0A` 用于对端按 LF 分帧。串口或仅有一条已连接会话的 TCP 可用 `{"id":"bytes-01","data":"01020304"}` 直接发送。

```json
{"id":"can-01","data":"01020304","meta":{"frame":{"id":"0x123"}}}
```

### 发送回执

```json
{"id":"udp-01","status":"sent"}
```

```json
{"id":"udp-01","status":"failed","error":{"code":"send_failed","message":"传输接口未接受数据"}}
```

`sent` 表示本地发送接口接受数据，设备收妥和执行结果需通过设备协议确认。回执可按下行 `id` 关联。重复 ID 的命令仍会分别处理，上行响应有独立的消息 ID。若命令在读取有效 ID 之前被拒绝，回执使用代理生成的 ID。

| 错误码 | 触发条件 |
| --- | --- |
| `invalid_json` | UDP 或 CAN 正文无法解析为 JSON 对象 |
| `invalid_request` | 命令字段缺失、类型错误、值超范围、HEX 无效或本地端点与配置不一致 |
| `payload_too_large` | 下行正文超过 1 MiB |
| `retained_command` | 命令到达代理时带 RETAIN 标志 |
| `send_failed` | 通道未接受发送，例如 TCP 目标不可用或 UDP 目标不在白名单中，具体原因见日志 |
| `unknown_device`、`stopped` | 处理器收到目标未绑定或代理已停止的命令。通常只订阅启用设备的命令 Topic，回执也依赖 MQTT 连接 |

## 旧格式兼容

`message_format: "legacy"` 只控制输出。UDP 上行为 `edge.udp.v1` JSON，含 `msg_id`、`src_ip`、`src_port`、`ts`、`replay`、`len` 和 HEX `data`。CAN 上行为 `edge.can.v1` JSON，含 `msg_id`、`can_id`、`extended`、`rtr`、`dlc`、`ts`、`replay` 和 HEX `data`。两者的格式名均在 `schema` 字段中，`replay` 固定为 `false`。TCP/串口上行为分帧后的原始字节。

旧回执使用 `schema: "edge.command-result.v1"`，含 `device_id`、`msg_id`、`operation`、`stage`、`code`、`message`、`ts` 和 `result`。有解析出的连接 ID 时，还会在顶层和 `result` 中带 `connection_id`。成功时 `stage` 为 `sent` 且 `code` 为 `ok`，失败时 `stage` 为 `failed`。

下行根据正文选用解析方式，所有输出格式均支持下列入口。

- TCP 和串口先检查正文能否解析为 JSON 对象。解析不出对象，或对象中没有 `data`、`operation`、`id`、`ts`、`transport`、`meta` 中的任何一个字段时，原始正文直接发送。即使原始业务 JSON 中只有 `msg_id` 或 `connection_id`，也走此规则。
- 进入对象解析后，含 `id`、`ts`、`transport` 或 `meta` 中任意字段时使用统一格式校验。与旧字段混用会失败。没有这些字段，也没有旧格式标记时，使用统一格式，例如仅含 `data` 的命令。
- 旧格式标记包括 `msg_id`、`operation`、`schema`、`target_ip`、`target_port`、`connection_id`、`can_id`。旧命令需要 HEX `data`，可使用 `msg_id` 关联回执。`operation` 省略时为 `send`，填写时只能是 `send`。UDP 另需 `target_ip` 和 `target_port`。CAN 另需 `schema: "edge.can.v1"`、`can_id`、`extended`、`rtr` 和 `dlc`。
- 旧格式和原始字节发送保留旧 TCP 路由。服务端用 `connection_id` 指定会话，未指定时从连接表取一个候选，选择顺序未定义。客户端直接使用当前连接，忽略旧 `connection_id`。需要验证连接身份时使用统一格式的 `meta.connection`。
