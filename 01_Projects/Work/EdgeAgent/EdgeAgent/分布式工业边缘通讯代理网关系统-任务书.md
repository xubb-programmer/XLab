# 分布式工业边缘通讯代理网关系统

## 项目任务书

> 文档版本：1.3
> 更新日期：2026-09-12
> 文档状态：开发基线（Baseline）

### 1. 项目基本信息

| 项目 | 内容 |
| :--- | :--- |
| 项目名称 | 基于 libmosquitto 与 Mosquitto Broker 的分布式工业多协议边缘代理系统 |
| 核心产品 | `EdgeAgent` 无界面边缘代理守护进程 |
| 配套产品 | `HostClientDemo` 上位机示例、Broker 部署配置、集成手册 |
| 核心定位 | 将串口、CAN、TCP、UDP 物理通道抽象为可治理的 MQTT 设备接口，隔离现场硬件与业务 UI |
| 目标部署 | 工业 PC、嵌入式 Linux 板卡、Windows 工控主机 |
| 主要技术 | C++、Qt 5、QtSerialPort、QtNetwork、Qt Serial Bus、libmosquitto、SQLite |

### 2. 建设目标

1. 上位机只依赖 MQTT Topic 和数据契约，不直接链接现场硬件 SDK。
2. 单个 Agent 支持多路串口、CAN、TCP 会话和 UDP 通道并发运行。
3. 任一物理通道掉线、拔出、校验失败或 Bus-Off 时，只影响自身并可异步恢复。
4. 通过统一的身份、权限、状态、资产和错误模型支持分布式运维。
5. 在 Broker 短时不可用时，按通道策略持久化关键采集数据，并在恢复后有序补发。

### 3. 范围与边界

#### 3.1 本项目范围

- 物理驱动生命周期管理、参数配置、收发和故障隔离。
- MQTT 连接、认证、订阅、发布、路由、在线状态和资产上报。
- Raw 和 JSON 两种通道载荷模式。
- 配置校验、日志、指标、健康检查、优雅退出和开机自启。
- 关键 JSON 采集通道的 SQLite Store-and-Forward。
- HostClientDemo 对指令、数据、状态和错误 Topic 的演示。

#### 3.2 不在本项目范围内

- 现场协议的业务语义解析、数据点建模和控制策略。
- Broker 集群、跨机房容灾和工业防火墙本身的建设。
- 对所有厂商 CAN 适配器的驱动开发。
- 通过 MQTT 直接保证物理设备的业务级幂等；设备协议仍需提供或配合幂等机制。

### 4. 系统角色与总体架构

```text
┌──────────────────────┐       MQTT/TLS       ┌────────────────────┐
│ HostClientDemo/业务系统 │ <──────────────────> │ Mosquitto Broker   │
└──────────────────────┘                       └─────────┬──────────┘
                                                         │
                          MQTT/TLS                      │
              ┌──────────────────────────────────────────┴───────┐
              │                                                  │
      ┌───────▼────────┐                                ┌────────▼───────┐
      │ EdgeAgent A     │                                │ EdgeAgent B    │
      │ 串口/CAN/TCP/UDP │                                │ 串口/CAN/TCP/UDP│
      └─────────────────┘                                └────────────────┘
```

- **EdgeAgent**：现场通道所有者，负责物理 I/O、协议边界校验和 Topic 路由。
- **Broker**：负责认证后的消息中继，不负责解释物理协议。
- **HostClientDemo/业务系统**：只使用 MQTT，不访问现场设备。
- **运维系统**：订阅状态、Inventory、错误和指标 Topic。

### 5. 平台与能力矩阵

| 平台 | MQTT | 串口 | TCP | UDP | CAN | 备注 |
| :--- | :---: | :---: | :---: | :---: | :---: | :--- |
| Linux x86_64 | 必须 | 必须 | 必须 | 必须 | 必须（SocketCAN） | 完整基线平台 |
| Linux ARM64/ARM32 | 必须 | 必须 | 必须 | 必须 | 必须（SocketCAN） | 以目标板卡实测为准 |
| Windows x64 | 必须 | 必须 | 必须 | 必须 | 可选 | CAN 只有在配置并安装受支持的厂商/适配器 Backend 后才纳入验收 |

Windows 不得宣称支持 Linux SocketCAN；CAN 驱动必须通过 `ICanBackend` 抽象隔离平台差异。没有可用 Backend 时，Agent 应报告该通道不可用，不得影响其他通道。

### 6. 技术和协议基线

- MQTT 3.1.1 为本期必选协议；MQTT 5.0 作为兼容扩展，不改变 v1 Topic 和载荷契约。
- 生产环境必须使用 TLS 和认证；明文 TCP 1883 仅允许开发机本地回环或明确的测试环境使用。
- Topic 统一使用 `edge/v1` 版本前缀，禁止通过修改字段含义实现不兼容升级。
- 下行控制默认不 Retain；状态和 Inventory Retain；具体 QoS、重试和重复语义以需求规格说明为准。
- JSON 载荷必须使用 UTF-8，二进制数据使用大写 HEX；Raw 载荷为 MQTT PUBLISH 的二进制 Payload。

### 7. 核心交付物

1. `EdgeAgent`：C++/Qt 无界面守护进程，包含配置、驱动、路由、可靠性和运维模块。
2. `config.json` 及 JSON Schema：包含 Broker、安全、通道、重试和 Store-and-Forward 配置。
3. `HostClientDemo`：演示 MQTT 认证、设备控制、数据订阅、状态和错误处理。
4. Broker 配置：TLS、账号、ACL、Topic 权限及开发环境示例。
5. 《工程部署与通信集成手册》：包含安装、升级、回滚、交叉编译、Topic、载荷和故障排查说明。
6. 测试交付物：单元测试、协议契约测试、故障注入测试、性能报告和验收记录。

### 8. 关键非功能目标

以下为本期基线指标，测试环境和样本数据必须写入验收报告：

| 指标 | 基线目标 |
| :--- | :--- |
| 并发能力 | 单 Agent 至少 32 个逻辑通道；TCP 并发会话数由配置给出并纳入测试 |
| 路由延迟 | 本地网络、80% 目标吞吐下，Agent 收到 MQTT 消息至写入物理驱动 p95 ≤ 50 ms |
| 启动时间 | 配置有效且 Broker 可达时，进程启动并完成通道初始化 ≤ 10 s |
| 故障隔离 | 单通道拔出、Bus-Off、非法报文或驱动异常不导致进程退出，其他通道持续工作 |
| 恢复策略 | 物理通道和 Broker 均采用指数退避重试，初始 1 s，最大 60 s，并记录每次状态变化 |
| 数据可靠性 | `store_forward=true` 的 JSON 通道在配置容量内持久化；恢复后按原始时间顺序补发，不静默丢弃 |
| 安全 | 生产连接启用 TLS、身份认证和最小权限 ACL；未授权发布/订阅必须被 Broker 拒绝 |
| 稳定性 | 完成不少于 24 小时混合通道压力和故障注入测试，无进程崩溃和未处理异常 |

### 9. 验收范围

验收至少覆盖以下场景：

1. 每类物理驱动的正常收发、配置错误、断开、重连和优雅退出。
2. MQTT Broker 重启、网络分区、TLS/认证失败、重复消息和非授权 Topic 访问。
3. CAN 标准帧、扩展帧、远程帧、非法 ID、数据长度错误和 Bus-Off 恢复。
4. TCP Server/Client 分帧、半包、粘包、多连接和连接超时。
5. UDP 单播、广播/组播、来源地址校验和长度错误报文。
6. Store-and-Forward 的进程重启、磁盘满、队列满、恢复补发和重复去重。
7. Retained 状态/Inventory、LWT 离线、状态恢复和多 Agent 设备 ID 冲突。
8. 性能、内存、CPU、日志可观测性及 24 小时稳定性测试。

### 10. 实施约束与风险

- 设备协议未提供幂等能力时，QoS 1 或补发可能造成重复执行；必须在通道配置中显式选择风险策略。
- TCP 和串口均为字节流，必须由通道配置提供明确的分帧规则，不能把 MQTT 消息边界当作物理帧边界。
- Store-and-Forward 依赖本地磁盘可靠性；容量、保留时间和满载策略必须可配置并告警。
- `node_id` 和 `device_id` 是系统身份，不得重复；身份冲突必须在启动或注册阶段阻止通道进入 READY。
