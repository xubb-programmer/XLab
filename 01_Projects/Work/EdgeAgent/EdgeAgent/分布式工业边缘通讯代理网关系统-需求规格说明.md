# 分布式工业边缘通讯代理网关系统

## 需求规格说明书

> 文档版本：1.3
> 更新日期：2026-09-12
> 文档状态：开发基线（Baseline）
> 关联任务书：[分布式工业边缘通讯代理网关系统-任务书.md](./分布式工业边缘通讯代理网关系统-任务书.md)

### 1. 文档目的与范围

本文档定义 `EdgeAgent` 的功能、通信协议、配置、可靠性、安全性和验收要求。本文档是开发、联调、测试和交付的共同基线。

EdgeAgent 负责现场物理通道与 MQTT Broker 之间的协议适配和路由，不负责解析现场业务语义，不负责替代 Host GUI 的业务逻辑。

#### 1.1 规范性词语

- **必须**：验收必需，不满足即不通过。
- **应**：默认实现要求；如需偏离，必须在配置或设计记录中说明。
- **可以**：可选扩展，不作为本期基础验收项。

#### 1.2 v1 基线边界

- MQTT 3.1.1 为必选；MQTT 5.0 为兼容扩展。
- Linux x86_64、Linux ARM 为完整基线平台。
- Windows x64 基线支持串口、TCP、UDP 和 MQTT；CAN 只有在安装受支持的厂商/适配器 Backend 后才支持。
- CAN v1 只支持经典 CAN 2.0A/2.0B，不把 CAN FD 纳入基础验收。
- IPv4 为基础验收范围；IPv6 可以作为后续扩展。

### 2. 术语、身份和约束

| 名称 | 定义 |
| :--- | :--- |
| `node_id` | EdgeAgent 节点身份，在部署范围内必须全局唯一 |
| `device_id` | 业务设备身份，在 Broker 的 Topic 命名空间内必须全局唯一 |
| `channel_id` | Agent 内部物理通道身份，在单个配置文件内必须唯一 |
| Raw | MQTT PUBLISH Payload 直接承载二进制数据；不自动 Base64、不自动 JSON 化 |
| JSON | UTF-8 JSON 信封，字段、类型和约束由本文档定义 |
| 物理帧 | 经串口/TCP 分帧器、CAN 报文或 UDP 数据报确认的一次完整数据单元 |
| Store-and-Forward | Broker 不可用时将指定上行数据持久化，恢复后重新发布 |

`node_id`、`device_id`、`channel_id` 必须匹配：

```text
^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$
```

身份不得包含 `/`、`+`、`#`、空格或控制字符。Agent 启动时必须拒绝重复的 `channel_id` 或 `device_id`；重复身份的通道不得进入 READY 状态。

### 3. 系统架构与线程模型

```text
┌──────────────────────┐       MQTT/TLS       ┌────────────────────┐
│ HostClientDemo/业务系统 │ <──────────────────> │ Mosquitto Broker   │
└──────────────────────┘                       └─────────┬──────────┘
                                                         │
                          MQTT/TLS                      │
              ┌──────────────────────────────────────────┴───────┐
              │                                                  │
      ┌───────▼────────┐                                ┌────────▼───────┐
      │ EdgeAgent A     │                                │ EdgeAgent B    │
      │ MQTT + 路由      │                                │ MQTT + 路由     │
      │ 串口/CAN/TCP/UDP │                                │ 串口/CAN/TCP/UDP│
      └─────────────────┘                                └────────────────┘
```

#### 3.1 模块职责

- **Config**：加载、校验和生成不可变运行配置。
- **MqttClient**：管理认证、连接、订阅、发布、LWT 和 MQTT 回调。
- **Router**：根据精确 Topic 与 `device_id` 查找通道，不解析现场业务语义。
- **Drivers**：封装 Qt 串口、Qt Serial Bus、Qt Network 以及平台专用 CAN Backend。
- **FrameCodec**：执行串口/TCP 分帧、JSON Schema、HEX、长度和地址校验。
- **StoreForward**：对启用的 JSON 上行通道进行本地持久化和有序补发。
- **Inventory/Health**：发布资产、通道状态、错误、指标和版本信息。

#### 3.2 线程和队列要求

1. `mosquitto_loop_start()` 可以运行 MQTT I/O 线程；MQTT 回调线程不得直接执行可能阻塞的物理 I/O、磁盘 I/O 或 JSON 大量处理。
2. MQTT 回调收到消息后必须复制 Payload 和 Topic，并投递到有界的路由队列；队列满时必须记录错误并按通道策略拒绝或丢弃，禁止无限增长。
3. 每个物理通道必须有独立状态机、输入队列、输出队列和超时/重试计时器。实现可以使用独立线程，也可以使用非阻塞事件循环，但不得让一个通道的阻塞操作占用其他通道。
4. Qt `QObject` 必须在所属线程创建和销毁；跨线程信号必须使用队列连接或等价的线程安全消息队列。
5. 所有线程必须在优雅退出时有确定的停止顺序和超时；超时后必须记录现场，不得静默泄漏。

### 4. 平台支持矩阵

| 平台 | MQTT | 串口 | TCP | UDP | CAN | 基线说明 |
| :--- | :---: | :---: | :---: | :---: | :---: | :--- |
| Linux x86_64 | 必须 | 必须 | 必须 | 必须 | 必须（SocketCAN） | 完整基线平台 |

### 5. MQTT 通信契约

#### 5.1 连接和安全

- 生产连接必须使用 TLS；推荐端口 `8883`。明文 `1883` 只允许本机回环或明确的开发环境。
- 必须验证 Broker 证书主机名和有效期；禁止通过关闭证书校验解决联调问题。
- 支持用户名/密码或客户端证书认证；密码不得明文写入 `config.json`，应通过受保护的环境变量、系统密钥存储或权限受限文件提供。
- `client_id` 默认使用 `edgeagent-{node_id}`，必须稳定且全局唯一。
- `keepalive_s` 默认 30 秒，可配置范围为 10~120 秒；Agent 必须在网络隔离或 Broker 无响应时进入 OFFLINE/RECONNECTING 状态。
- 重连采用指数退避，初始 1 秒，最大 60 秒，并加入随机抖动，避免多个节点同时重连。
- v1 默认 `clean_session=true`，Broker 不得为离线 Agent 排队下行控制消息；上位机必须依据状态决定是否重发。

#### 5.2 Topic 约定

所有 Topic 使用 `edge/v1` 前缀。变量只能占用单层 Topic，不得包含 `/`、`+` 或 `#`。

| 方向/用途 | Topic | QoS | Retain | 说明 |
| :--- | :--- | :---: | :---: | :--- |
| 下行控制 | `edge/v1/devices/{device_id}/commands` | JSON=1，Raw=0 | 否 | Host 发布，Agent 只订阅自己配置的设备 |
| 上行数据 | `edge/v1/devices/{device_id}/data` | 默认 0，可配置为 1 | 否 | Agent 发布，Host 订阅 |
| Agent 应答 | `edge/v1/devices/{device_id}/command-results` | 1 | 否 | JSON 下行的接收/写入结果 |
| 设备/通道错误 | `edge/v1/devices/{device_id}/errors` | 1 | 否 | 结构化错误事件 |
| 节点状态 | `edge/v1/gateways/{node_id}/status` | 1 | 是 | `online`/`offline`/`ready`/`degraded` 状态 |
| 硬件信息 | `edge/v1/gateways/{node_id}/hardware` | 1 | 是 | 当前配置和硬件能力 |
| 节点指标 | `edge/v1/gateways/{node_id}/metrics` | 0 | 否 | 可选周期统计信息 |
| 节点错误 | `edge/v1/gateways/{node_id}/errors` | 1 | 否 | 不属于单个设备的错误 |

Agent 禁止默认订阅 `edge/v1/devices/+/commands`。启动时必须按配置对每个 `device_id` 建立精确订阅；若设备数量很多，可以由 Broker ACL 和受控的单层通配符共同限制范围。

下行 TX 禁止 Retain。收到 `retain=true` 的 TX 消息必须拒绝执行并发布错误事件，防止历史指令在 Agent 重连后重放。

#### 5.3 重复、顺序和应答

- QoS 1 只保证至少一次投递，不能视为 exactly-once；Agent 和 Host 都必须允许重复事件。
- JSON TX 必须包含 `msg_id`，格式为 UUID 或调用方保证全局唯一的字符串，长度不超过 64 字节。
- Agent 对最近处理过的 `msg_id` 保留可配置的去重窗口，默认 10 分钟；重复消息不得再次写入物理设备，但应返回 `duplicate` 应答。
- `ack` 至少区分 `accepted`、`sent`、`failed`、`duplicate` 四种阶段，并包含 `msg_id`、`ts`、`code` 和 `message`。
- Raw TX 不携带统一 `msg_id`，默认 QoS 0、无重试、无 Agent 级别应答；需要可靠重试的物理协议必须自行携带序号或使用 JSON 模式。

#### 5.4 时间戳

- `ts` 为 Agent 采集或接收物理帧的 UTC Unix epoch 毫秒数。
- Agent 必须使用系统 UTC 时钟，并在 hardware/metrics 信息中报告时间同步状态；不得把本地时区字符串当作 `ts`。
- 不能确认系统时钟可靠时，仍可转发数据，但必须产生 `clock_unsynchronized` 告警。
- 补发消息必须保留原始 `ts`，并额外设置 `replay=true`；补发顺序按持久化序号和原始 `ts` 的稳定排序确定。

### 6. 载荷契约

#### 6.1 通用规则

- JSON 使用 UTF-8，禁止 NaN、Infinity 和未知的必填字段类型。
- HEX 使用偶数长度的大写字符集 `[0-9A-F]`；空数据使用空字符串。
- Agent 必须验证字段类型、长度、范围和协议约束；验证失败不得写入物理端口。
- 全局 `max_payload_bytes` 默认 1 MiB，超限消息必须拒绝并产生错误事件。

#### 6.2 Raw 模式

Raw 模式的每个 MQTT PUBLISH 对应一个完整物理帧或一个由通道分帧器产生的完整数据单元。Raw Payload 是二进制，不做 Base64 和 JSON 转换。

Raw 模式不表示串口或 TCP 变成了消息协议：串口/TCP 仍是字节流，必须先根据配置完成分帧。v1 Raw 通道不支持 Store-and-Forward；需要时间戳、补发和去重的通道必须使用 JSON 模式或由现场协议自行携带元数据。

#### 6.3 CAN JSON 信封

下行 Topic：`edge/v1/devices/{device_id}/commands`

```json
{
  "schema": "edge.can.v1",
  "msg_id": "7f4c7a11-4b40-4ae5-9a5e-ff8bc9c17f43",
  "can_id": "0x18FF50E1",
  "extended": true,
  "rtr": false,
  "dlc": 8,
  "data": "A102FF0011223344"
}
```

上行 Topic：`edge/v1/devices/{device_id}/data`

```json
{
  "schema": "edge.can.v1",
  "msg_id": "b1dd6d32-13e2-4f3d-b2f3-3a8bdc9c70b8",
  "can_id": "0x18FF50E1",
  "extended": true,
  "rtr": false,
  "dlc": 8,
  "ts": 1715678901234,
  "replay": false,
  "data": "A102FF0011223344"
}
```

CAN v1 约束：

- `can_id` 使用 `0x` 前缀十六进制字符串；标准帧范围为 `0x000`~`0x7FF`，扩展帧范围为 `0x00000000`~`0x1FFFFFFF`。
- `extended=false` 时不得使用超过 11 位的 ID；`extended=true` 时允许 29 位 ID。
- 经典 CAN 的 `dlc` 范围为 0~8，且必须等于 `data` 十六进制字符数除以 2。
- `rtr=true` 时 `data` 必须为空，`dlc` 表示请求长度；不支持以数据段伪造远程帧。
- v1 不接受 CAN FD 字段；收到包含不支持字段的报文必须拒绝并告警。

#### 6.4 UDP JSON 信封

下行 Topic：`edge/v1/devices/{device_id}/commands`

```json
{
  "schema": "edge.udp.v1",
  "msg_id": "d3d1e3b1-0e1e-43a2-89e5-6f87d7c2b4f0",
  "target_ip": "192.168.1.105",
  "target_port": 6000,
  "data": "010300000002C40B"
}
```

上行 Topic：`edge/v1/devices/{device_id}/data`

```json
{
  "schema": "edge.udp.v1",
  "msg_id": "65fd564a-ec45-4546-a9f0-74cfbaadbd15",
  "src_ip": "192.168.1.105",
  "src_port": 6000,
  "ts": 1715678901235,
  "replay": false,
  "len": 9,
  "data": "01030400010002A1B2"
}
```

UDP 约束：

- `target_port`、`src_port` 范围为 1~65535；`len` 必须等于 `data` 的字节数，Agent 必须自行计算并校验。
- `bind_address`、网卡、组播地址、广播开关和允许的对端必须由配置明确指定，不能默认监听所有网卡并接受任意来源。
- 接收到的来源 IP/端口不在允许列表时必须丢弃并记录安全事件。
- v1 以 IPv4 为基础；IPv6 需要单独声明 Backend 和测试覆盖。

### 7. 配置需求

#### 7.1 配置加载和校验

1. 配置路径由 `EDGEAGENT_CONFIG` 指定；未指定时使用可执行文件目录下的 `config.json`。
2. 配置必须先通过 JSON 语法和 Schema 校验，再创建任何物理通道。
3. 全局配置错误、Broker 安全配置错误或身份冲突必须使进程进入 NOT_READY 并返回非零退出码。
4. 单个通道配置错误只阻止该通道进入 READY，其他合法通道继续运行；错误必须进入日志和状态/错误 Topic。
5. 配置变更默认需要重启生效；v1 不要求热加载，禁止在未验证新配置时覆盖当前有效配置。
6. 密钥、私钥和密码不得写入日志；配置文件权限必须限制为运行账户可读。

#### 7.3 通道类型要求

| 类型 | 必填配置 | 额外要求 |
| :--- | :--- | :--- |
| `serial` | `port`、`baud`、数据位、校验、停止位、流控、`frame` | 支持 1200~921600；端口值按平台解释 |
| `can` | `backend`、`interface`、`bitrate`、`filters` | v1 为经典 CAN；Linux 基线使用 SocketCAN |
| `tcp` | `role`、监听或远端地址/端口、`frame` | `role` 为 `server` 或 `client`；Server 必须限制最大连接数 |
| `udp` | 绑定地址/端口、允许对端、广播/组播配置 | 禁止隐式监听所有地址并接受任意来源 |

`frame.kind` 至少支持 `idle_timeout`、`delimiter`、`fixed_length`、`length_prefix` 四类；TCP/串口必须明确一种，不能使用“自动猜测”。每个通道必须独立维护分帧状态和计时器，并显式配置最大帧长度。

### 8. 功能性需求

#### FR-01 配置与启动

- Agent 启动时必须完成配置加载、Schema 校验、平台能力检查和身份冲突检查。
- 全局配置有效后，逐通道创建驱动；单通道失败不得使其他合法通道退出。
- 启动日志必须包含 Agent 版本、配置版本、`node_id`、平台、Broker 地址（不得包含密码）和每个通道的初始状态。
- 启动完成后，Agent 发布 Inventory 和状态；若仍有通道错误，状态必须为 `degraded` 而非 `online` 的无条件成功状态。

#### FR-02 串口驱动

- 使用 Qt SerialPort 或等价封装，支持 RS232/RS485。
- 支持 1200~921600 波特率、数据位、校验位、停止位和流控配置。
- 按配置执行分帧；收到半帧、超长帧、校验失败或超时必须按通道策略处理并计数。
- 物理拔出时进入 `DISCONNECTED`，使用退避策略重试；重连成功后发布状态变化和 Inventory 更新。
- RS485 半双工收发方向控制必须明确由平台驱动或外部硬件完成；Agent 不得假定所有适配器行为相同。

#### FR-03 CAN 驱动

- Linux 使用 Qt Serial Bus 的 SocketCAN Backend；Windows 使用配置的 `ICanBackend`。
- 支持标准帧、扩展帧、远程帧、过滤器和收发错误报告。
- 检测 Bus-Off 并执行配置的恢复动作；恢复失败时继续周期重试，不得阻塞其他 CAN 或非 CAN 通道。
- 发送前必须校验 ID、扩展标志、RTR、DLC 和数据长度；接收后必须生成符合 6.3 的 JSON。

#### FR-04 TCP 驱动

- 支持 Client 主动连接和 Server 监听两种角色。
- 支持配置最大连接数、连接/读写超时、心跳周期、心跳响应和断线重连。
- 必须使用配置的分帧器处理半包、粘包和多帧合并；不能按 `readyRead` 次数判断帧边界。
- Server 多连接必须有稳定的会话 ID；每个会话的异常不得关闭其他会话。
- `QTcpSocket` 的 Raw Payload 只代表完整分帧结果，不代表 TCP 本身具有消息边界。

#### FR-05 UDP 驱动

- 支持指定网卡/绑定地址、单播、广播和组播接收；组播必须明确组地址和网卡。
- 下行必须校验目标地址是否在允许范围；上行必须记录真实来源地址和端口。
- 发送失败、报文超长、来源不允许或 JSON 校验失败时，必须产生可观测错误，不得将非法数据发布为 RX。
- 对 UDP 不做可靠传输承诺；需要可靠性必须由上层协议或 Store-and-Forward 策略提供。

#### FR-06 MQTT 路由

- MQTT 连接建立后，Agent 只订阅配置中属于自身的 `edge/v1/devices/{device_id}/commands`。
- 收到 TX 后按 Topic 精确查找通道，校验 Retain、QoS、Payload 大小、模式和 JSON/HEX 规则。
- Unknown device、Unknown channel、Topic 格式错误、非法载荷和不允许来源必须拒绝，并发布错误事件。
- 路由过程不得阻塞 MQTT 回调线程；物理写入必须通过通道队列执行。
- JSON TX 按 `msg_id` 去重并发布 ACK；Raw TX 依照 5.3 的无应答、无重试约束执行。
- 上行有效物理帧必须在校验和分帧后发布 RX；JSON 模式增加 `ts`、`msg_id` 和 `replay`，Raw 模式原样发布。

#### FR-07 状态、LWT 和 Inventory

- MQTT 连接前通过 LWT 注册 `edge/v1/gateways/{node_id}/status`，Payload 为 `offline`，QoS=1，Retain=true。
- 连接并完成订阅后发布 `online`；只有 MQTT 已连接且通道初始化完成才允许发布 `ready`，否则发布 `degraded`。
- 正常收到退出信号时，先停止接受新 TX、完成或明确失败已有操作，再发布 `offline` 并断开 MQTT。
- Hardware 信息必须包含 `schema`、`node_id`、Agent 版本、平台、生成时间、通道列表、物理能力、配置摘要和当前状态；不得泄露密码、私钥或完整证书内容。
- Hardware 信息必须在启动、通道增删/重连、配置变更和硬件状态变化时更新；Retained 内容不得无限期保持与实际状态不一致。

#### FR-08 Store-and-Forward

- `store_forward.enabled=true` 的通道必须使用 SQLite WAL 或等价的持久化队列；仅内存环形队列不得作为关键通道的实现。
- v1 只允许 JSON 上行通道启用 Store-and-Forward；Raw 通道启用时配置校验必须失败。
- 启用 Store-and-Forward 的通道必须使用 QoS=1；QoS=0 只能作为非持久化实时采集使用。
- 每条记录至少保存 `channel_id`、稳定序号、原始 `ts`、Payload、重试次数和状态。
- Broker 不可用或发布未确认时写入本地队列；Broker 恢复后按稳定序号顺序补发，并标记 `replay=true`。
- 队列有最大字节数、最大记录数和最大保存时间；到达上限时必须产生告警并执行明确的 `overflow_policy`，禁止静默丢弃。
- Agent 重启、进程崩溃恢复后不得重复确认已完成记录；即使发生重复发布，Host 也必须依据稳定序号或 `msg_id` 去重。
- 磁盘不可写、数据库损坏或迁移失败时，通道进入 `DEGRADED`，继续尝试采集但必须持续告警。

#### FR-09 日志、指标和运维

- 日志级别至少包括 `error`、`warn`、`info`、`debug`；生产默认 `info`。
- 每条错误必须有稳定 `code`、发生时间、节点、通道（如适用）、摘要和恢复建议。
- Metrics 至少包括 MQTT 连接状态、收发计数、丢弃数、队列深度、重连次数、物理错误、Store-and-Forward 待补发数和最近成功时间。
- 提供进程退出码、健康检查或等价的本地诊断接口；不得依赖 GUI 判断 Agent 是否存活。

### 9. 非功能需求

#### NFR-01 故障隔离

- 任一通道拔出、Bus-Off、非法输入、驱动异常、数据库错误或 TCP 会话异常不得导致 Agent 进程崩溃。
- 不得使用无限重试、无限队列或阻塞式全局锁；单通道故障不得阻塞其他通道和 MQTT 心跳。
- C++/Qt 异常、线程入口异常和第三方库错误必须在边界捕获、记录并转换为通道状态。

#### NFR-02 性能与容量

- 单 Agent 至少支持 32 个逻辑通道；具体混合通道组合必须写入测试报告。
- 在本地网络、80% 目标吞吐下，MQTT 入站到物理写入 p95 ≤ 50 ms；测试必须注明消息大小、Broker、硬件和 CPU。
- 默认单 Payload 上限为 1 MiB；超限拒绝且不得造成内存持续增长。
- 进程启动并完成初始化目标不超过 10 秒；单通道重连不应阻塞全局启动和其他通道。

#### NFR-03 可用性和恢复

- 物理通道和 Broker 重连使用 1~60 秒指数退避和抖动。
- keepalive=30 秒时，网络黑洞场景下 Broker 应在不超过 60 秒内观察到 Agent 离线；实际值必须由测试验证。
- 完成 24 小时混合通道压力和故障注入测试，无进程崩溃、未处理异常和静默数据丢失。

#### NFR-04 安全

- 生产环境使用 TLS、证书校验、认证和最小权限 ACL。
- Agent 只能订阅自身设备 commands，只能发布自身设备 data/command-results/errors 和自身节点 status/hardware/metrics。
- 配置、日志、Core Dump 和诊断输出不得暴露密码、私钥或敏感 Token。
- 对 JSON 深度、字段数量、字符串长度、HEX 长度、IP/端口范围和消息频率进行限制，防止资源耗尽。

#### NFR-05 数据一致性

- JSON 字段类型、HEX 大小写、长度、ID 范围和 Topic 变量必须可由自动化契约测试验证。
- 所有带 `ts` 的消息必须使用 UTC epoch 毫秒；补发保留原始 `ts` 并设置 `replay=true`。
- QoS 1、重连和补发造成的重复必须可识别、可记录、可去重；不得宣称 MQTT 提供 exactly-once 物理执行。

#### NFR-06 可维护性

- 配置 Schema、Topic、JSON Schema、错误码和版本号必须纳入版本控制。
- 升级不得覆盖有效配置和本地 Store-and-Forward 数据；必须提供回滚和数据库迁移策略。
- 关键设计决策、平台 Backend、测试硬件和已知限制必须写入集成手册。

### 10. 验收用例矩阵

| 编号 | 场景 | 通过条件 |
| :--- | :--- | :--- |
| AT-01 | 配置语法、Schema、重复身份 | 非法全局配置拒绝启动；单通道错误不影响其他合法通道 |
| AT-02 | 串口收发与拔插 | 正常分帧；拔出只影响该通道；恢复后自动重连 |

| AT-04 | TCP 半包/粘包/多连接 | 按配置分帧；连接互不影响；心跳和超时有效 |

| AT-06 | MQTT 路由和权限 | 只处理自身设备；TX Retain 被拒绝；ACL 越权操作失败 |

| AT-10 | 安全与压力 | TLS/认证/ACL 生效；达到基线吞吐和 24 小时稳定性指标 |

### 11. 版本和兼容性策略

- `edge/v1` 的 Topic 和已有字段含义不得在兼容升级中改变。
- 新增字段必须保持接收方对未知可选字段的兼容；改变必填字段、类型或语义时必须升级 Topic 版本。
- Agent、HostClientDemo、JSON Schema 和 Broker ACL 必须一起发布兼容版本。
- 升级前必须校验配置版本、备份配置和 Store-and-Forward 数据；升级失败时恢复到上一可运行版本。
