## 二、处理过程

### 1. 发送端网卡切换

初始状态：`eth1` 启用，地址为 `192.168.0.201/24`；`eth0` 关闭。现场将地址迁移到 `eth0` 后，反馈如下：

```text
eth0 UP   192.168.0.201/24
eth1 DOWN
```

当时路由仅显示局域网直连路由，没有默认网关。同网段通信不依赖默认网关。

结果：网卡切换在当次运行中生效。此前使用的是 `ip` 命令，未提供永久网络配置验证结果；不能据此认定重启后保留。

### 2. 核实 EdgeAgent 服务名称

最初尝试使用 `edgeagent` 作为 systemd 服务名，系统提示单元不存在。

检查部署源码发现：程序可执行文件名为 `edgeagent`，部署服务名实际为 `server-edge.service`。服务加载 `/etc/intelligent-cooperative-server/edgeagent.json`。

此前将可执行文件名等同于服务名的判断不准确，后续已按实际服务名排查。

### 3. 区分两条 TCP 通道

现场实际配置确认如下：

| 设备 ID | 通道 ID | 接收地址 |
| --- | --- | --- |
| fire-01-device | fire-01-tcp | 192.168.10.102:5567 |
| fire-02-device | fire-02-tcp | 192.168.0.102:5567 |

日志中的连接错误属于 `fire-01-tcp`；同时，`ss` 曾显示到 `192.168.0.102:5567` 的连接为 `ESTAB`。因此不能用第一条通道的错误判断第二条通道也失败。

### 4. 定位点位绑定缺失

网页提示“等待接收端回执超时”。订阅 `fire-02-device` 消息后，重新上报仍没有输出。

检查网页实际返回的场景，发现当前“1号作业单元”的编号为 `FIRE-7f7e2dc8fb317863791e07dd`，含 IP、端口和 `mountedDeviceId`，但没有 `deviceId`。

源码中的设备选择逻辑为：

```js
deviceId: point.deviceId || point.id
```

缺少 `deviceId` 时，后端使用点位编号作为 MQTT 设备 ID。该编号与 EdgeAgent 已配置设备不匹配。IP、端口和挂载设备字段不等同于这里的通信设备绑定。

现场完成实际场景绑定修正后，HTTP 查询确认 `deviceId` 已保存；随后 MQTT 出现了对应设备的命令和发送结果。这些证据支持绑定缺失是本次发送路由问题的原因。

### 5. 发现两份场景文件不一致

首次检查和修改的是持久化目录中的旧场景，内容为“地面作业点”，编号 `FIRE-01`。网页实际显示的却是另一条“1号作业单元”记录。

| 路径 | 现场内容及用途 |
| --- | --- |
| `/var/lib/intelligent-cooperative-server/scenarios/scenario-default.json` | 旧场景；当时并非网页实际读取的文件 |
| `/opt/jw/intelligent-cooperative-server/releases/d040e0fd7fa3b4af/web/public/scenarios/scenario-default.json` | 本次服务实际读取的发布目录场景 |

服务工作目录位于 `current/web`，现场环境文件中没有显式的场景路径覆盖；默认场景路径解析到了上述发布目录文件。

结果：首次修改未影响当前网页。后续修改实际读取的文件，通过 HTTP 返回确认“1号作业单元”的绑定生效。

持久性：已保存文件可在重启后保留，但位于发布目录，升级切换版本时不保证沿用。两份场景尚未统一。

### 6. 确认命令已进入 TCP 发送环节

现场 MQTT 观察结果：

```text
edge/v1/devices/fire-02-device/commands {"id":"…","transport":"tcp","data":"…"}
edge/v1/devices/fire-02-device/command-results {"id":"…","status":"sent"}
```

含义：网页命令已到达 EdgeAgent；EdgeAgent 的 TCP 写入调用接受了数据。

限制：`sent` 不证明接收端已完成业务处理，也不替代业务回执。

### 7. 检查接收端服务

接收端 `192.168.0.102` 的现场检查显示：

- `usb-mouse-sync.service` 为 `inactive (dead)`，当时未运行。
- 5567 端口当时没有监听。
- 已部署源码包含响应写入、执行结果等待及回执发送逻辑，不属于完全未实现回执。

现场随后启用服务并设置开机自启，确认服务为运行状态，Python 程序监听 `0.0.0.0:5567`。

此前发送端的 `ESTAB` 是较早时刻的状态；不能据此证明接收端服务在后来检查时仍然运行。

### 8. 恢复连接并收到业务失败回执

接收端启动后，发送端曾提示“传输接口未接受数据”。现场重启 `server-edge` 后，确认连接如下：

```text
192.168.0.201:41004 → 192.168.0.102:5567 ESTAB
```

接收端日志确认客户端接入、收到并处理 `Action` 请求，随后报告：

```text
USB HID link is not configured: not attached
```

网页显示了同一错误。由此确认 TCP 请求及失败业务回执均已贯通，故障已进入接收端 USB HID 执行环节。

## 三、USB 回执含义

源码执行路径为：TCP 请求校验 → 共享动作队列 → HID 动作执行 → 结果队列 → 原 TCP 连接返回 JSON。

HID 执行前会读取 USB 设备控制器状态。状态持续为 `not attached`，未达到期望的 `configured`，等待超时后抛出异常。服务捕获异常并返回 `ok: false`、错误文本及原请求的 `request_id`；响应末尾自动追加 LF 换行。

`not attached` 描述 USB 接口状态，不是以太网或 TCP 状态。它不单独确定线缆、接口、设备角色或主机识别中的哪一项异常。

网页显示“结果未知”的原因：该失败响应没有明确声明 `processed: false`；发送端按保守规则处理，不能保证动作完全未执行。不能把“收到失败回执”等同于“确认所有动作均未发生”。

现场动作配置已包含 `Action`，所以本次已排除默认示例动作名称不匹配这一猜测。

源码中还存在动作完成后才回执、共享队列串行执行、文件锁和 HID 阻塞写入等等待点。这些是潜在超时因素，但本次没有足够证据认定发生了锁死；最终明确错误是 USB 未配置。

### 2. 高精度离线地图排查与恢复
- **问题现象**：重新部署后三维态势底图仅能显示 0-5 级低精全国概览，放大至福建沿海（厦门/泉州）或朱日和-赤峰区域时瓦片缺失。
- **原因分析**：初次打包部署时由于排除了 `dist/` 构建输出目录，导致 `dist/offline-maps/combined-theaters/`（1.67GB 合并瓦片库及清单）未包含在部署包中，板端请求 `/offline-maps/combined-theaters/manifest.json` 返回 404。
- **处理措施**：
  1. 将合并图集 `tiles.db`（161,009 张瓦片，包含福建沿海 5,565 瓦片与朱日和-赤峰 155,444 瓦片，最高亚米级 18 级清晰度）通过流式传输同步至板卡 `/var/lib/intelligent-cooperative-server/offline-maps/combined-theaters/`。
  2. 经过 SHA256 校验对比（`feb42e6515d9c574853d3163b5890856d8aa11202cf0b3916a67ea7bccb4cd59`），双端字节完全一致。
  3. 图集清单 `manifest.json` 经中性化清洗（0 敏感词）后部署，通过软链接映射至 `web/dist/offline-maps/combined-theaters`，并已在 `install.sh` 中建立持久化映射机制。
- **验证结果**：
  - 清单接口 `GET /offline-maps/combined-theaters/manifest.json` 返回 HTTP 200，图层配置解析正常；
  - 福建区域宏观瓦片（`6/53/27.jpg`）与核心区超清瓦片（`17/108676/56306.jpg`）响应正常（HTTP 200）；
  - 朱日和-赤峰区域宏观瓦片（`6/51/23.jpg`）与核心区超清瓦片（`17/106597/48400.jpg`）响应正常（HTTP 200）。

  1. **UI 交互入口**：在网页「设置」主页面中新增「初始地图显示位置」专属配置卡片，提供中心经度、中心纬度、视点高度精确数值输入，并提供「朱日和·赤峰」、「东南沿海」、「全国概览」快捷预设。
  2. **地图交互点选**：点击「从地图点选拾取」后自动切至三维地球界面并悬浮状态条，操作员点击地图任意点位自动计算经纬度并提取当前视点高度，无缝切回设置面板填入输入框。

  4. **全链路联调**：通过自动化浏览器端到端测试，实测经纬高输入、地图点选、快捷预设切换、飞向预览与保存接口，全部执行通过。

4. 保存配置时验证引用存在，避免缺失字段退回业务编号后仅表现为回执超时。
5. 区分命令已提交、传输接受、执行成功、明确未处理和结果未知，减少误判。
6. 为排查提供按设备和请求编号筛选的日志，并记录请求接收、执行开始、执行结束和响应发送。
