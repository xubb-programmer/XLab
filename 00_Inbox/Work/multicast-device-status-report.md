# 组播上报设备状态

本文按 2026-11-12 的代码整理，没有在设备上抓包核对；示例报文是示意，不是实抓。

## 1. 两条通道

设备上有两个组播发送器，共用同一个目标地址，同一时刻只有一个在发：

| | 新版（协议 2.0 信封） | 旧版（扁平报文） |
|---|---|---|
| 实现 | `MediaServiceMulticastReporter.cpp` | `UdpMulticastSender.cpp` |
| 报文构建 | `HttpServer::buildMulticastReportSnapshotJson()` | `HttpServer::buildZLMSnapshotJson()` |
| 配置来源 | `MediaServiceConfig.ini` 的 `[multicast_report]` | `DeviceInfo.ini` 的 `multicast_ip` / `multicast_port` |
| 默认 | 关闭 | 开启，`239.255.0.1:5678` |
| 周期 | 可配，100–60000 ms，默认 1000 | 固定 1000 ms |
| TTL | 可配，1–255，默认 1 | 固定 32 |
| 源端口 | 绑定到组播端口本身（`SO_REUSEADDR`） | 系统分配的临时端口 |

- **互斥**：新版开启后旧版一帧都不发；新版关闭后归还给旧版。
- **地址同步**：新版配置成功时，会把 IP 和端口写回 `DeviceInfo.ini`，旧版目标跟着变。
- **启动**：新版配置持久化，启动时自动恢复，并在启动时就按持久化的开关决定归属。

设备状态接入平台时，由 EdgeAgent 加入上述组播地址并通过 MQTT 转发；网页服务订阅 `edge/v1/devices/plc_udp_multicast_dev/data`，不直接监听 UDP 组播。

## 2. 传输层

- UDP IPv4 组播，一个数据报就是一份完整的紧凑 JSON（UTF-8，无分帧、无分片协议）。
- 报文可能超过 MTU：代码注释记录同源的 SSE 快照约 11KB，依赖 IP 分片。
- `IP_MULTICAST_LOOP=1`，本机也能收到自己的包。
- 出口网卡每个周期重选一次：优先默认路由上有载波的网卡，没有候选时交给内核路由（`MulticastEgressInterface.h`）。

## 3. 新版报文（协议 2.0）

### 3.1 信封

| 字段 | 类型 | 说明 |
|---|---|---|
| `协议版本` | string | 固定 `"2.0"` |
| `设备ID` | string | `DeviceInfo.ini` 的 `device_id`，人工填写，可能重复 |
| `设备名称` | string | `device_name`，同上 |
| `设备序列号` | string | `/proc/device-tree/serial-number`，硬件唯一，应作为设备身份 |
| `设备IP` | string | 设备管理 IP；连 HTTP 接口应使用它，不要用包的源 IP |
| `时间戳` | string | 本帧发送时刻，`yyyy-MM-ddTHH:mm:ss±HH:MM`，本地时区 |
| `快照时间` | string | `数据` 的采集时刻，格式同上 |
| `序号` | integer | 从 1 递增，改配置不重置，进程重启后重新计数 |
| `数据` | object | 业务状态，见 3.2 |

```json
{
  "协议版本": "2.0",
  "设备ID": "ZTYL_01",
  "设备名称": "智图影链",
  "设备序列号": "xxxxxxxxxxxxxxxx",
  "设备IP": "192.168.10.130",
  "时间戳": "2026-11-12T10:00:01+08:00",
  "快照时间": "2026-11-12T10:00:00+08:00",
  "序号": 123,
  "数据": {
    "视频源列表": [],
    "推流通道列表": [],
    "宫格推流": { "desired": {}, "active": {} },
    "大屏输出": []
  }
}
```

### 3.2 `数据` 的四个字段

内容与对应的 `/status` 接口同源，每项同时带中文键、英文键和运行态 `active` 对象。

#### `视频源列表`（数组，对应 SSE 的“外部视频源列表”）

- 主要中文键：`视频源ID`、`视频名称`、`视频源地址`、`视频源协议`、`视频源开关`、`连接策略`、`连接状态`、`来源类型`、`托管类型`、`识别开关`、`识别状态`、`模型名称`、`中继开关`、`按需引用数`、`按需引用者`、`直拉引用者`、`持久化`。
- 按情况出现：`子码流`（`地址`/`宽度`/`高度`/`码率`）、`播放地址`、`发布地址`、`发布协议`、`接入方式`、`接入来源`、`重连已持续毫秒`、`重连剩余毫秒`、`重连次数`、`SRT接收参数`、识别错误相关字段。
- 远端副本（ID 以 `rmt_` 或 `remote-` 开头）一律不上报，防止设备间二次传播。
- 手动添加的源始终上报，且不带 `发布中`，表示是否有流未知。
- 本机 ZLM 里的源（自动同步、推流通道派生、HDMI 输出）只在流存在或正在重连时上报，并带两个字段：
  - `发布中`：ZLM 里当前是否有这路流，跨设备判断能否播放只看它。
  - `仅因重连保留`：流已不在，只因重连倒计时未结束而保留。
- 地址按实际发布协议改写：RTMP 发布的报 RTMP 播放地址，SRT 的报 `m=play` 播放地址。
- 本机流的地址主机保留回环写法，接收方需替换成 `设备IP`。

#### `推流通道列表`（数组）

- 主要中文键：`推流通道ID`、`视频源地址`、`视频名称`、`视频源名称`、`推流地址`、`推流协议`、`编码格式`、`视频宽度`、`视频高度`、`推流码率`、`码率模式`、`推流开关`、`连接状态`。
- 按情况出现：`SRT发布参数`、`链路分段`、`srt_link`、`重连…毫秒`、`源消失已持续毫秒`、`源消失剩余毫秒`。
- SRT 推流地址在上报里改成可播放的 `m=play` 地址。

#### `宫格推流`（对象，`{desired, active}`）

- `desired`：`宫格名称`、`宫格数量`、`放大位置`、`行数`、`列数`、`推流协议`、`推流地址`、`编码格式`、`推流开关`、`视频宽度`、`视频高度`、`推流码率`、`帧率`、`子码流策略`、`宫格列表`（每项 `宫格位置`/`视频源地址`/`视频名称`）。
- `active`：`running`、`connection_state`、`focus_state`、`active_slots`、`screen_outputs`、`error_reason` 等。
- `宫格名称` 只在上报里有：取指向同一路流的视频源名称，否则是“<设备名>-宫格”。

#### `大屏输出`（数组，每个 HDMI 口一项）

- `输出接口`、`输出开关`、`输出模式`、`视频源地址`、`视频名称`、`识别跟随`、`实际显示`、`连接状态`，以及 `active`。

## 4. 发送行为（新版）

- 采集和发送是两个线程：采集慢或失败时，继续按周期发上一份快照。
- `快照时间` 不变而 `时间戳` 在走，说明数据已停滞；超过 5 秒设备会记日志。
- 开启后要等第一份快照采集成功才发第一帧，不会发空数据。
- 关闭再开启会清掉缓存，重新采集。
- 发送失败的帧也占用序号，接收端看到的跳号能和设备日志 `[组播上报] 组播发送失败` 对上。
- 通过 `/setting/deviceInfo` 改设备 ID 或名称，下一帧立即生效。

## 5. 配置接口

### `POST /setting/multicastReportConfig`

解析在 `MediaServiceHttpRoutes.cpp` 的 `parseMulticast()`。

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `组播开关` | bool | 是 | |
| `上报周期毫秒` | integer | 是 | 100–60000 |
| `组播地址` | string | 开启时必填 | IPv4 组播段 224.0.0.0–239.255.255.255 |
| `组播端口` | integer | 开启时必填 | 1–65535 |
| `TTL` | integer | 否 | 1–255，默认 1 |

- 关闭时可以不带地址和端口；带了就按同样规则校验，并同步给旧版。
- 成功的 reason 是 `multicast_report_updated`。
- 错误 reason：`missing_required_field`、`invalid_multicast_period`、`invalid_multicast_address`、`invalid_multicast_port`、`invalid_multicast_ttl`（均 400）、`port_in_use`（409）、`config_write_failed`（500）。

### `GET /status/multicastReportConfig`

- 返回持久化的 `组播开关`、`组播地址`、`组播端口`、`上报周期毫秒`、`TTL`。
- 它反映的是新版配置，不是旧版 `DeviceInfo.ini` 里的目标。

## 6. 旧版扁平报文

没有信封，所有字段在一层：

- 设备信息：`设备编号`、`设备名称`、`序列号`、`设备IP`。
- ZLM 状态：`推流列表`（当前 ZLM 流地址数组）、`推流状态`、`错误原因`。
- 业务状态：`外部视频源列表`、`推流通道列表`、`宫格推流`、`大屏输出`。

与新版的差别：

- 字段名不同：`设备编号` 对应新版 `设备ID`，`序列号` 对应 `设备序列号`，`外部视频源列表` 对应 `视频源列表`。
- 没有 `协议版本`、`序号`、`时间戳`、`快照时间`。
- 视频源条目不带 `子码流`，且包含远端副本。
- 内容与 ZLM 的 SSE 事件数据完全一致。

接收端可以用是否存在 `协议版本` 区分两种报文。

## 7. 上报里的流地址

### 7.1 本机 ZLM 的地址格式

本机 ZLM 的流以 `app/stream` 标识，与协议无关，三种协议的地址写法：

| 协议 | 端口 | 格式 |
|---|---|---|
| RTSP | 554 | `rtsp://<主机>:554/<app>/<stream>` |
| RTMP | 1935 | `rtmp://<主机>:1935/<app>/<stream>` |
| SRT | 9000 | `srt://<主机>:9000?streamid=#!::r=<app>/<stream>,m=play` |

- SRT 的 `app/stream` 在 `streamid` 的 `r=` 里，不在路径里；`m=play` 是播放，`m=publish` 是发布。
- 子码流固定用 `sub` 作为 app、流名不变：`rtsp://<主机>:554/sub/<stream>`，SRT 则是 `r=sub/<stream>`。

### 7.2 各字段给的是什么地址

| 位置 | 字段 | 含义 | 主机 |
|---|---|---|---|
| `视频源列表[]` | `视频源地址`（同 `url`） | 这路源的拉流地址 | 本机流为 `127.0.0.1`；外部源为原地址 |
| `视频源列表[]` | `视频源协议`（同 `protocol`） | 与 `视频源地址` 配套的协议 | |
| `视频源列表[]` | `子码流.地址` | 子码流拉流地址 | 同主地址 |
| `视频源列表[]` | `播放地址` | 仅中继源：本机 ZLM 上的回读地址 | `127.0.0.1` |
| `视频源列表[]` | `发布地址` / `发布协议` | 本机把这路流发布进 ZLM 用的地址 | |
| `推流通道列表[]` | `视频源地址` | 通道的输入 | |
| `推流通道列表[]` | `推流地址`（同 `url`） | 通道的输出；SRT 时已改成播放地址 | 回环改成 `设备IP`，外部目标不变 |
| `宫格推流.desired` | `推流地址`（同 `url`） | 宫格输出；SRT 时已改成播放地址 | 同上 |
| `宫格推流.desired.宫格列表[]` | `视频源地址` | 每格的输入 | |
| `宫格推流.active.active_slots[]` | `source_url` | 每格当前实际在播的地址 | 回环改成 `设备IP` |
| `宫格推流.active.screen_outputs[]` | `source_url` | 每个大屏当前实际显示的地址 | 回环改成 `设备IP` |
| `大屏输出[]` | `视频源地址` | 大屏配置的输入 | |

主机写法不统一：`视频源列表` 里本机流保留 `127.0.0.1`，接收方必须替换成信封的 `设备IP`；推流通道、宫格的 SRT 输出和运行态 `source_url` 已经是 `设备IP`。

### 7.3 `视频源列表` 的地址改写规则

持久化配置和 `/status/videoSourceList` 里，本机流的回读地址一律是 `rtsp://127.0.0.1:554/<app>/<stream>`。上报副本（组播和 SSE）按这路流实际的发布方式改写 `视频源地址` 和 `视频源协议`：

| 源的类型 | 判断依据 | 上报地址 |
|---|---|---|
| 宫格输出（含宫格子码流） | 宫格推流协议是 SRT | `srt://127.0.0.1:9000?streamid=#!::r=<app>/<stream>,m=play` |
| 宫格输出 | 宫格推流地址是 RTMP | `rtmp://127.0.0.1:1935/<app>/<stream>` |
| HDMI 输出托管源 | `发布地址` 是 RTMP | `rtmp://127.0.0.1:1935/<app>/<stream>` |
| 推流通道派生源 | 对应通道的推流地址是 RTMP | `rtmp://127.0.0.1:1935/<app>/<stream>` |
| 外部推进来的自动源 | ZLM 报的接入方式是 `rtmp_push` | `rtmp://127.0.0.1:1935/<app>/<stream>` |
| 外部推进来的自动源 | 接入方式是 `srt_push` | `srt://127.0.0.1:9000?streamid=#!::r=<app>/<stream>,m=play` |
| 其余本机流 | RTSP 发布或拉流代理 | 不改，保持 `rtsp://127.0.0.1:554/...` |
| 手动添加的源 | | 不改，用户填的原地址 |
| 中继源 | | 不改，`视频源地址` 是监听地址 |

- 判断发布协议时先看地址的 scheme，地址没有 scheme 才看协议字段。
- 外部推进来的自动源，接入方式只在流还在 ZLM 里时才有；流断了（因重连保留）会回落成 RTSP 地址。
- 宫格输出和 HDMI 输出的 `子码流.地址` 由改写后的主地址推导，协议和主机与主地址一致。

### 7.4 SRT 输出地址的改写

`推流通道列表` 和 `宫格推流` 里，凡是协议为 SRT 且地址的 `streamid` 带 `r=<app>/<stream>` 的，上报时都改成播放地址：

- `m=publish` 换成 `m=play`，其余 `streamid` 参数丢弃。
- 主机是 `127.0.0.1` 或 `localhost` 时换成 `设备IP`，其他主机不变；端口不变，缺省补 9000。
- `streamid` 里没有 `r=<app>/<stream>` 的地址原样上报。
- `/status` 接口仍返回持久化的发布地址，只有上报副本被改写。

### 7.5 旧版 `推流列表`

- 字符串数组，每 2 秒从 ZLM 的 `getMediaList` 刷新一次，去重，顺序不固定。
- RTSP/RTMP 条目取 ZLM 的 `originUrl`，主机换成 `设备IP`（取不到 IP 时为 `127.0.0.1`）并补默认端口。
- SRT 条目按 `app/stream` 重建为 `srt://<设备IP>:9000?streamid=#!::r=<app>/<stream>,m=play`。
- ZLM 接口请求失败时列表为空。
- 新版信封不带这个字段；新版用它在内部判断 `发布中`。

## 8. 如何判断 HDMI_IN 是否接入设备

这里的“接入设备”指 HDMI_IN 口接了信号源。

### 8.1 背景

- HDMI_IN 有信号时，设备采集画面并推进本机 ZLM；拔掉后停止推流，流随之消失。
- 推流目标由 `/setting/pushStream` 配置，常用值是 `live/stream`，但现场可以改成别的 `app/stream`。
- 这路流在视频源列表里对应一条 `托管类型` 为 `hdmi_output` 的托管源。

### 8.2 不要只看 `live/stream` 是否存在

| 现象 | 不能直接得出的结论 | 原因 |
|---|---|---|
| 有 `live/stream` | HDMI_IN 已接入 | 别的设备也能往本机 ZLM 的 `live/stream` 推流；推流地址也可能已改成别的 |
| 没有 `live/stream` | HDMI_IN 未接入 | 推流开关关闭、推流失败或正在重建、ZLM 异常时流同样不在 |

### 8.3 推荐的判断方式

**新版组播（协议 2.0）**

1. 在 `数据.视频源列表` 里找 `托管类型` 等于 `hdmi_output` 的条目。
2. 看它的 `发布中`：
   - `true`：HDMI 输入有信号，且已成功推进 ZLM。
   - `false`，或找不到该条目：当前没有这路流。
3. 不能只看条目是否存在：拔线期间这条源可能因重连保留而仍在列表里，此时 `发布中` 为 `false`、`仅因重连保留` 为 `true`。

这种方式不依赖具体的流地址，推流地址改了也有效。

**旧版组播（扁平报文）**

- 看 `推流状态` 和 `错误原因`，它们就是 HDMI 推流的状态。
- 再用 `推流列表` 里是否有配置的推流地址做佐证。

**HTTP 接口（最直接）**

- `GET /status/deviceStatus` 返回 HDMI_IN 的 `接口状态`。
- 它来自硬件状态文件 `hardware_status.ini` 的 `hdmi_in_connected`，反映物理连接，与推流是否成功无关。

### 8.4 局限

- 组播里的判断得到的是“HDMI 画面是否已发布成流”，不是物理连接状态。接了设备但推流关闭或失败时，结果是“未发布”。
- HDMI_IN 的物理接口状态目前不在组播报文里，只能通过 HTTP 接口取。若接收端需要只靠组播判断物理接入，要在信封里增加该字段。
